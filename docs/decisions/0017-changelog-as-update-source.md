# 0017. 更新情報の正本を changelog データに一元化し、RSS・トップ新着を導出する

- 日付: 2026-06-11
- ステータス: 採択
- 関連 PR: feat/changelog-driven-updates

## 背景

RSS フィードは法令ページの lastVerified 降順一覧だった(pubDate = lastVerified、description = 法令 summary 固定)。この設計には 2 つの問題がある:

- **「何が変わったか」が配信されない。** 公式解説の改訂やページ追加は更新履歴ページに記録されるが、フィードには流れない
- **内容変更のない再浮上が起きる。** 鮮度棚卸し(`docs/freshness-audit.md`)で lastVerified だけが動くと、内容が変わっていないのにフィード上で全法令が新着扱いになる

また、トップページに更新の表示はなく(Highlights は静的な代表解説)、更新履歴ページの各項目は該当ページへのリンクを持たないため、更新を見ても 1 クリックで辿れなかった。4 サイト横断のリピート訪問性分析(2026-06)で、これらが law の最優先課題と整理された。

## 決定

1. 更新履歴データを `src/data/changelog.ts` に抽出し、**サイトの更新情報の正本**とする。`/changelog/`(表示)・`/rss.xml`(配信)・トップ「最近の更新」(直近 3 日付)はすべてここから導出する
2. RSS は changelog ベースに置き換える。**1 日付 = 1 アイテム**とし、title は先頭項目の種別ラベル+本文先頭 60 字(複数項目時は件数を付記)、description は全項目の列挙、link は `/changelog/#d-{date}` とする
3. 各項目は対象ページへの `links`(label + href)を持てる。付与基準は**対象ページが一意に特定できる項目のみ**。サイト横断の変更はリンクなし、または一覧ページへのリンクとする。label は法令名 / ガイドの短名(ADR 0016 の表記)を使う

## なぜこの判断にしたか

- **changelog は PR ごとに必ず更新される運用**(ユーザー向け変化のある PR は同 PR 内で追記)のため、追加の編集コストなしに RSS・トップ新着が自動で追随する
- **1 日付 = 1 アイテムにするのは guid(= link)の一意性のため。** 項目単位で配信すると、同一ページに複数項目が紐づいたときに link が重複し、フィードリーダーに重複排除される恐れがある。日付アンカーへのリンクなら常に一意
- **lastVerified 順フィードの並存は見送り。**「最終確認しただけ」の日付変動はフィードではノイズであり、内容のある変更は changelog に必ず載るため、changelog ベースが情報量で上位互換になる

## 帰結

- 既存の購読者には、移行時に全日付が新規アイテムとして一度だけ流れる
- 更新履歴への追記時は、対象ページが一意なら `links` を付けるのが標準の運用になる
- トップ「最近の更新」は `changelogEntries.slice(0, 3)` の自動表示のため、手動更新(従来の Highlights のような静的配列)は不要
