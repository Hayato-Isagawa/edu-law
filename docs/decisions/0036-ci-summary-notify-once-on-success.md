# 0036. PR の Actions が全部成功したときだけ、PR に 1 回だけ通知する(ci-summary・追認記録)

- 状態: 採用
- 日付: 2026-11-19
- 関連 PR: #266(導入・2026-09-19)・#269(起動条件の修正)・#359(重複防止の印を bot のコメントからだけ拾う)。本 ADR はその決定を後から記録する
- 関連 ADR: [`0032`](0032-e2e-required-check.md)(E2E の赤を知らせる通知が無いことを前提にしている)

## 背景

GitHub Mobile の「ワークフロー実行」の通知は、workflow run 1 本ごとに届く(2026-09-19 実測)。PR 1 本で
Build・E2E・VRT などが走るので、PR 1 本で通知が 2〜4 回鳴っていた(#266)。

2026-09-19 に #266 で `.github/workflows/ci-summary.yml` を足し、通知を 1 回にまとめた。ファミリーでは
このリポが最初で、同じ日のおよそ 3 時間後にファミリーの各リポも同じ workflow を入れた(edu-evidence PR #632・
edu-watch PR #714 など)。方針の一部は `ci-summary.yml` の冒頭のコメント・`CLAUDE.md`・`CONTRIBUTING.md`・
ADR 0032 に書かれているが、決定として記録した ADR はどのリポにも無い。本 ADR を原本とし、姉妹リポはこれをミラーとして引く。

## 検討した選択肢

当時の検討の記録は無い。以下は #266 の本文と `ci-summary.yml` のコメントから組み立て直したもの。

1. **通知をそのまま受ける** — 却下。PR 1 本で何度も鳴り、どれが最後かも分からない
2. **ワークフロー実行の通知を切り、何も受けない** — 却下。PR がマージできる状態になったことに気づけない
3. **失敗も集約 workflow から知らせる** — 却下。集約 workflow 自身を赤にすると、それが別の通知源になる
   (`ci-summary.yml` の冒頭)
4. **全部成功したときだけ、PR に @メンション付きのコメントを 1 件付ける** — 採用

## 決定

- PR の commit に付いた **GitHub Actions の check-run が全部完了し、全部成功**したときだけ、その PR に
  管理者への @メンション付きのコメントを 1 件付ける。GitHub Mobile では「ダイレクトメンション」の通知として
  1 回だけ届く。`skipped` と `neutral` は成功として扱う(人の PR では Dependabot auto-merge の job が
  `skipped` で終わる)
- **失敗したときは何もしない。** 集約 workflow 自身を赤にすると、それが別の通知源になるため
- **見るのは GitHub Actions の check-run だけ。** Cloudflare Workers Builds の check-run は `workflow_run` を
  起こさないので、それを待つと再判定の機会が無く、通知が黙って消える
- **起動元の workflow の `conclusion` では絞らない。** 最後に完了した workflow が `skipped` だと再判定が走らず
  通知が消える経路があったため(#269)。成否は check-run の走査が全件で見る
- **Dependabot の PR は対象外にする**(#266 から。外した理由は #266 に書かれていない)
- **同じ commit には 1 回だけ。** コメントに commit の SHA を含む印を入れ、github-actions[bot] のコメントにだけ
  印を探す。公開リポなので、誰かが印を先に書けば通知を止められてしまうため(#359)

起動する workflow の列挙・権限・判定の本体の正典は `ci-summary.yml` で、
`scripts/__tests__/ci-summary-workflow.test.mjs` が workflow 全体を固定している。本 ADR には列挙を写さない。

## 帰結

### 良い帰結

- PR 1 本で何度も鳴っていた通知が、成功したときの 1 回になる
- 「通知が来た = その commit の Actions が全部成功した」と読める

### コストと受け入れた死角

- **失敗はこの仕組みでは通知されない。** 赤に気づく経路は PR の check 一覧を見ることだけになる。
  Dependabot の PR は成功も通知しない(ADR 0032 は、この死角を理由の 1 つに挙げて E2E を required に
  した)
- **壊れても静かに壊れる。** 判定が崩れて通知が消えても workflow は exit 0 で終わる。このため、
  workflow 全体と `run:` の本文をテストで固定している(`CLAUDE.md` の `test:workflows` の節)
- **`workflow_run` は既定ブランチの定義で、対象リポの書き込みトークンで走る。** fork からの PR でも同じ。
  権限は `checks: read` と `pull-requests: write` だけにし、`run:` に渡すイベント由来の値は head の SHA と
  PR 番号だけにしている(PR 側が任意の文字列にできる値を展開しない)
- **PR 起動の workflow を足したら、`workflows:` の列挙にも足す必要がある。** 足し忘れると、その workflow の
  完了では再判定が走らない。列挙と各 workflow の `on:` の突き合わせはテストが見ている
- **Workers Builds の結果は待たない。** プレビューのビルドが失敗していても、Actions が全部成功していれば
  通知は届く

### 反対意見

**通知の受け方は管理者個人の作業嗜好で、ADR の対象外ではないか。** ADR の README は「個人の作業嗜好」を
対象外に置いている。通知を 1 回にまとめたいというきっかけ自体は嗜好に近い。

それでも ADR にするのは、この決定がリポの中身として公開リポに残り、他人にも見えるため。全 PR にコメントが
付き、書き込みトークンで走る `workflow_run` を 1 本抱え、失敗を通知しないという死角を ADR 0032 のような
別の決定が前提にしている。ファミリーの各リポが同じ workflow を持つので、どれが原本かも決めておく必要がある。

## 撤回 / 再検討の条件

- GitHub Mobile の通知の単位が変わり、workflow run ごとに鳴らなくなった場合
- 失敗の見落としが実際に起き、失敗も通知する必要が出た場合(そのときは通知源を増やさない形を別 ADR で決める)
- 書き込みトークンで走る `workflow_run` の危険が、通知をまとめる利点を上回ると判断した場合
